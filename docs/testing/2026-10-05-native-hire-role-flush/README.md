# Native prepared-hire role-write ordering

A project-enrolled native hire persists its persona/role assignment after its
exact controller and delivery receipt are adopted. Starting its completion watch
before that write finished could put the assignment and role receipt between the
project guard's two settings reads. The unchanged revision fence then retired the
controller despite the write belonging to the hire it had just admitted.

The hire keeps synchronous adoption and delivery-receipt reconciliation behind
its final authority proof. Its own asynchronous role flush finishes before new
completion/status watches and the fleet-change publication. A matching durable
completion watch is registered before adoption without starting it, preserving
the uncertain-hire claim if watch persistence fails. Pending role writes retain
their existing journal/recovery behavior.

Already-running completion watches can probe during live-controller reuse. The
same store serializes project guard snapshots with its adoption role flushes.
External settings changes, changed conversation authority, native process/session
identity and project/capacity checks remain fenced; no retry accepts a changed
revision. These changes apply to local native controllers without remote code.

The existing native fleet lifecycle integration journey now enrolls its positive
prepared hire in an actual project (`fixture(true)`). It crosses the real Captain,
loopback controller, native plugin/runtime, UNIX Herdr fixture and SQLite history
boundaries, then reconciles its roster and closes only the original native TUI.
No live owner state, remote machine, provider, credentials or evals are used.

Exact-HEAD repeated acceptance receipts and the base race trace live in the
worker handoff under `.local/evidence/VUH-1555/`. The integrator owns landing.
